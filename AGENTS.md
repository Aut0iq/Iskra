# AGENTS.md — Iskra

Guidance for coding agents working in this repository. English is the
language of code, docs and commits.

## What this is

Two parts in one tree:

- **Zeron plugin** — `plugin/iskra/` (Luau): `init.luau` entry,
  `model.luau` pure status model, `zeron.luau` vendored SDK,
  `locales/`, `assets/` generated by `scripts/build-plugin.py`
  (`animations.luau` + `v6/` frames — never hand-edit, regenerate).
  Manifest: `zeron-plugin.json` (signature is stripped on staging).
- **Desktop companion** — `src/` (Rust, GTK4 + gtk4-layer-shell):
  `zeron.rs` read-only MCP transport, `model.rs` status model,
  `behavior.rs` placement/reactions, `desktop.rs` surfaces + HUD,
  `launcher.rs` detached `--launch` path, `usage.rs` cache reader,
  `assets.rs` manifest validation/hot-reload,
  `src/bin/prepare_assets.rs` deterministic asset prep.
- **Packaging** — `scripts/`: `build-plugin.py` (unsigned staging),
  `build-companion.sh` (deterministic tarball), `install-companion.sh`
  (transactional installer), `stage-plugin.sh` (live-folder copy with
  backup), `tests/test_packaging.py`.

## Conventions

- Deterministic builds and assets: `SOURCE_DATE_EPOCH` pinned,
  manifest-driven frame lists, atomic publishes. Regenerate rather than
  patch generated output.
- Fixture-first tests; the real app is never a test fixture.
- Rust: `cargo fmt --check`, `cargo clippy --offline --all-targets --
  -D warnings`, `cargo test --offline` must stay green; no new
  dependencies without a stated reason.
- Shell/Python packaging scripts: POSIX `sh`, stdlib Python (+ Pillow
  only where already required).
- Comments explain intent, not diffs; match surrounding terseness.
- Current laptop branding is the owner-approved Raspberry Flame;
  follow `docs/BRANDING.md`. Older image-generation records contain
  superseded Arch-logo instructions, not current branding guidance.

## Hard boundaries

- **No secrets, no consent bypass.** Never read or commit credentials,
  keys, or Zeron `.state`/key material. Signing and permission consent
  are human actions in Zeron; scripts never perform or fake them.
- **No public writes without explicit owner authorization.** No `git push`, package publishing, release
  uploads, or signing/exporting plugins for distribution.
- **No real app launches.** Never start the GTK companion, Zeron, or
  any user's running application; never send input or kill processes
  you did not spawn for a fixture. Verification uses temp dirs,
  fake executables, and headless gates only.
- **Docs stay honest.** No badges, owner URLs, license claims, or
  shipped-feature claims that are not true yet.

## Branches, CI and delivery (mandatory)

- Never push main or create/move/delete release/nightly tags. All work starts
  from dev in feature-name or bugfix-name. External contributors use forks;
  upstream write ACL remains owner plus the scoped automation App.
- PRs target dev. Only upstream dev may target main. CI performs promotion
  after the required CI Gate succeeds. No bypass, force push or skipped gate.
- A direct dev push is owner-only and exceptional: warn and require explicit
  acknowledgement through the pre-push hook. Prefer PRs even for the owner.
- Install the local hook with git config core.hooksPath .githooks. It is
  feedback; native GitHub rules are the actual security boundary.
- The dedicated automation App is required for strict CI-only tags/updates.
  Never weaken rules to make a release succeed or use an owner's token as
  the permanent bypass. If App provisioning is absent, publishing stays closed.
- Stable tags/releases originate from current main and a fully green exact-SHA
  CI run. Dev produces immutable nightly tags with UNSIGNED staging marked
  as such. Never publish unsigned staging as an installable plugin.
- Zeron signing/export and permission consent remain human-only. CI verifies
  the public Ed25519 signature and exact reviewed payload, never signs.
- Windows/macOS packages are portable Zeron plugins/avatar tools. The native
  desktop companion runs on Linux/Wayland (GTK4 + gtk4-layer-shell) and on
  Windows via the reviewed Win32 layered-window port (`desktop_win.rs`);
  macOS remains unported.
- Avatar packs are data/images only. Preserve authorship/licensing, validate
  paths, alpha/dimensions and size, and reject symlinks or executable content.
  Runtime theme/avatar switching is not shipped by defining a schema.
- docs/DEVELOPMENT.md documents enforceable rules, administrative limits,
  native App provisioning and the checks needed before each delivery.
